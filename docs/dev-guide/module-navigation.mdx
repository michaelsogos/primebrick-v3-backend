# Module navigation metadata

`src/modules/module-nav-meta.ts` resolves **which frontend routes belong to
which module** (`resolveModuleNavMeta`). The FE never hardcodes navigation —
it fetches this metadata; the AI assistant navigates through it; the
generated `navigation-map.mdx` doc derives from it.

## Two sources, one contract (`ModuleNavWithPrefixes`)

```ts
{
  module: "crm",
  route_prefixes: ["/crm"],                       // coarse ownership
  is_reserved?: true,
  nav: [ {id, label_key, href, icon, children?} ], // sidebar tree
  routes: [ {route, kind, entity?, label_key?, component_url?, component_format?} ],
}
```

| Source | Owner | Use |
|---|---|---|
| `MODULE_NAV` (static registry) | **BE-owned modules only** — currently just the reserved `settings` shell | Bootstrap nav for the platform itself |
| `service_registry.endpoints.nav` | **Service-owned modules** (job, emailsender, crm, …) | Self-declared in the `service.register` payload, validated at enrollment by `validateNavDeclaration` — a malformed declaration is rejected and can never poison `/modules` or the census |

A module presents **only its own nav** — Settings MUST NOT declare links to
service-owned pages (a service going offline would orphan them, and the
module would masquerade as part of Settings). Settings therefore declares
only the prefix its own routes live under — `/system/settings` — never a
`/system` catch-all.

## Root level (`part_of`) — module namespace

Every module has a **root level** (`service_registry.part_of`, persisted at
registration) and a **module code** (`service_registry.code`). Together they
form the module's single route namespace:

- **Standard**: `/{part_of}/{code}` — `job` (`part_of: "system"`) owns
  `/system/job/**`; `settings` (`part_of: "system"`) owns `/system/settings/**`.
- **Collapse**: when `part_of === code` the module IS its own root level and
  the segment collapses to `/{code}` — `crm` (`part_of: "crm"`) owns `/crm/**`.

`validateNavDeclaration` enforces this at `service.register` time:
`route_prefixes` must CONTAIN the computed primary prefix, and every
`nav[].href` and `routes[].route` must live under SOME declared prefix —
a module can never declare pages on a foreign prefix or a foreign code.

**Extra root memberships (multi-root):** `route_prefixes` may add entries
of the form `/{other-root}/{code}` — the module code stays the URL's
second segment under every root. A crm service can therefore own `/crm/**`
(primary) AND `/system/crm/**` (extra): the pipeline page lives at
`/system/crm/pipeline` while customers stay at `/crm/customers`. Each
extra prefix materializes its first segment as an additional app level in
the FE launcher; ownership still resolves by longest-prefix. Single-segment
extras (`/foo`) and foreign-code segments (`/system/other`) are rejected.

**Default module (`is_default`):** `service_registry.is_default` marks the
module as the default of its OWN root (`part_of`). At most one winner per
root: a registration claiming `is_default` demotes the previous winner
(keep-winner policy — a re-registering service never downgrades an
admin's later choice; the claim is an upgrade-only flag). `/api/v1/modules`
returns `part_of` + `is_default` so the FE app launcher can group modules
by app level and resolve app-click → default module → first page.

Three layers, each with a distinct consumer:

| Layer | Purpose |
|---|---|
| `nav[]` | The **sidebar tree** — label keys, icons, hrefs. FE renders it verbatim via `fetchModuleMeta`. **Module home = `nav[0].href`** (single source of truth for the module switcher) |
| `route_prefixes` | Coarse ownership — "every path starting here belongs to this module" (last-resort coverage; powers `isLinkActive` longest-match in the sidebar) |
| `routes: PageRouteDeclaration[]` | The **complete census** — every FE path the module owns, incl. detail/create/param routes not deducible from nav links, each typed `list \| detail \| create \| page`, optionally bound to an `entity` and/or a remote `component_url` + `component_format` (`esm-mount`) |

**Modules MUST declare every path they own.** A route missing from the
census is invisible to the AI and to the generated navigation map.

**Icons:** the module/service icon lives on `service_registry.icon` (the
sole module icon — there is no top-level `nav.icon`); per-page icons are
the `nav[].icon` fields and resolve through `DynamicIcon`.

## Consumers

1. **FE sidebar** — `AppSidebar` → `GET module meta` → renders `nav[]`.
   Nested routes activate exactly one link: the longest matching href wins.
2. **`RoutesCensusService`** (`GET /system/routes`) — aggregates per
   enabled service: declared `routes` + nav `href`s + `route_prefixes`.
   Remote-delivery fields (`component_url`, `component_format`,
   `integrity`) flow through to the FE verbatim — they are the route's
   resolution config. Powers the guide assistant's `search_routes` client
   tool — answers *"where do I find X?"* with real paths. Cached 30s
   in-process.
3. **`generate:docs`** — `generate-reference-docs.ts` iterates
   `listModuleNavCodes()` + the service registry to emit
   `docs/user-guide/generated/navigation-map.mdx` (route → module → kind
   → entity). No FE file scanning — the metadata already knows everything
   a `+page.svelte` scan could find and more.

## Adding a service module's routes

Publish `endpoints.nav` in the service's `service.register` payload —
`route_prefixes` + `nav[]` + full `routes` census. One declaration makes
the module appear in the sidebar, the census, the AI's navigation answers
and the generated doc at the next `generate:docs`. BE-owned modules add a
case to `MODULE_NAV` instead.
